# Бизнес-требования: Idea-to-Jira MVP

**Статус:** актуальная базовая версия для MVP
**Версия:** 1.0
**Дата:** 2026-08-20
**Целевой контур:** production
**Язык документа:** русский

## 1. Назначение

Idea-to-Jira MVP — публичный Telegram-бот на базе выделенного OpenClaw, который помогает автору структурировать продуктовую идею и, при наличии доверенной роли Creator, автоматически создаёт Feature в Jira.

Документ фиксирует бизнес-цели, границы, роли, правила и критерии успеха. Детальная логика приведена в `FUNCTIONAL_REQUIREMENTS.md`, контракт создания Jira — в `JIRA_CREATE_CONTRACT.md`, зафиксированные решения — в `DECISIONS.md`.

## 2. Приоритет источников

При расхождениях применяются в следующем порядке:

1. решения из `DECISIONS.md`;
2. настоящий документ и остальные актуальные документы каталога `docs/`;
3. исходное ТЗ версии 1.0 от 2026-08-20.

В частности, устаревшие требования исходного ТЗ о preview, confirmation token и кнопке «Создать в Jira» к MVP не применяются.

## 3. Бизнес-проблема

Авторы идей передают инициативы в разном формате и с разной полнотой. Product Owner тратит время на уточнение контекста, проблемы, ожидаемого эффекта и маршрута. При этом публичный канал нельзя наделять неконтролируемым правом создавать Jira-задачи.

MVP должен одновременно:

- уменьшить объём ручного первичного оформления;
- повысить единообразие Feature;
- предложить обоснованную маршрутизацию по продукту и командам;
- предупредить создание очевидных дублей;
- обеспечить контролируемый допуск к production Jira;
- оставить продуктовое решение и дальнейший workflow за PO.

## 4. Цели MVP

### BR-001. Структурирование идеи

Система должна преобразовывать текст или голосовое сообщение автора в структурированный Draft и уточнять только недостающие сведения.

### BR-002. Контроль доступа

Любой Telegram-пользователь может подготовить собственный Draft, но Jira Feature может быть создана только для пользователя с активной ролью Creator.

### BR-003. Доверие к личности

Для Guest корпоративная личность не считается подтверждённой самим Telegram ID, username или display name. Доверие к связке «Telegram sender ID — конкретный пользователь» возникает только в результате решения уполномоченного Business Admin. Это решение выдаёт роль Creator и должно быть аудируемым.

### BR-004. Автоматическое создание без лишнего шага

Для Creator Jira Feature должна создаваться автоматически, когда текущий Draft готов и завершено обязательное решение по дублям. В MVP нет отдельного preview, confirmation token и кнопки создания.

### BR-005. Предотвращение дублей

Перед созданием система должна выполнить ограниченный поиск похожих задач в Jira, предварительно сузив область поиска с помощью Knowledge Catalog. Решение по найденным кандидатам принимает Creator.

### BR-006. Ограничение раскрытия Jira

Сведения о найденных Jira-дублях доступны только Creator. Guest не получает Jira key, ссылку, summary, описание или иные детали кандидатов.

### BR-007. Маршрутизация

Система должна предложить допустимый продукт и маршрут только на основании активной версии Knowledge Catalog и подтверждённых Jira options. Неизвестные продукты, команды и значения полей не должны выдумываться.

### BR-008. Уведомление PO

После подтверждённого создания Feature назначенный по каталогу Product Owner должен получить Telegram-уведомление. Дальнейшая работа выполняется в стандартном Jira-процессе.

### BR-009. Сохранение роли PO

Бот не принимает продуктовые решения вместо PO, не выполняет workflow transitions и не назначает исполнителя.

### BR-010. Production-ready пилот

MVP предназначен для production-контура. Он должен быть развёрнут в отдельном Docker-контейнере с отдельным OpenClaw на последнем стабильном релизе, выделенными данными, конфигурацией и секретами.

### BR-011. Голосовой ввод

MVP должен принимать Telegram voice messages в личных сообщениях и транскрибировать их локальным Whisper `medium`. Необходимые вычислительные ресурсы считаются доступными.

### BR-012. Аудит и управляемость

Система должна сохранять проверяемую историю допуска, изменений Draft, решений по дублям, попыток Jira create, результатов и уведомлений без записи секретов и полных приватных Jira-данных в технические логи.

## 5. Роли

### 5.1. Guest

Может:

- начать личный диалог с ботом;
- отправить идею текстом или voice message;
- отвечать на вопросы и редактировать свой Draft;
- запросить допуск Creator;
- получать статус заявки на допуск.

Не может:

- создавать Jira-задачи;
- видеть детали найденных Jira-дублей;
- видеть чужие Draft и заявки;
- управлять ролями;
- задавать Jira origin, project, issue type, JQL, field IDs или credentials.

### 5.2. Creator

Это Guest, чья identity была признана доверенной решением Business Admin и чья роль активна.

Дополнительно может:

- получать детали кандидатов на дубли;
- выбрать существующий дубль либо явно указать, что идея не является дублем;
- довести Draft до готовности;
- получить Jira key и ссылку после автоматического создания.

Creator не запускает create отдельной кнопкой: переход выполняется системой автоматически после выполнения всех предикатов готовности.

### 5.3. Business Admin

Может через детерминированные Telegram handlers без участия LLM:

- просматривать pending-заявки;
- сопоставлять Telegram sender ID с известной ему личностью;
- разрешать или отклонять роль Creator;
- отзывать, приостанавливать и восстанавливать допуск;
- блокировать пользователя;
- просматривать санитаризированный audit;
- получать операционные уведомления об ошибках, требующих вмешательства.

Business Admin не получает автоматически доступ к OpenClaw Gateway, хосту, filesystem или секретам.

### 5.4. Product Owner

- получает Telegram-уведомление после успешного create;
- открывает созданную Feature в Jira;
- валидирует идею и продолжает стандартный Jira workflow;
- при необходимости корректирует поля средствами Jira.

### 5.5. Technical Owner

- развёртывает и обновляет отдельный контейнер OpenClaw;
- управляет секретами, конфигурацией, backup/restore и диагностикой;
- обеспечивает Jira connectivity и локальный Whisper `medium`;
- выполняет ручную reconciliation операций `UNKNOWN`;
- не принимает продуктовые решения вместо PO.

### 5.6. OpenClaw как владелец Catalog

Knowledge Catalog является отдельным versioned результатом/задачей. OpenClaw выступает владельцем и актуализатором каталога. Процесс сбора, проверки, публикации и обновления каталога должен быть отдельно спроектирован и согласован до эксплуатационного запуска соответствующей версии данных.

## 6. Целевой бизнес-процесс

### 6.1. Подготовка Draft

1. Пользователь открывает DM с выделенным ботом.
2. Система привязывает данные к host-derived Telegram sender ID.
3. Текст вводится напрямую; voice message транскрибируется Whisper `medium`.
4. Пользователь может исправить распознанный текст.
5. Система извлекает факты, предложения и неизвестные значения, задаёт уточнения и версионирует Draft.
6. Guest при необходимости запрашивает роль Creator.

### 6.2. Допуск Guest

1. Создаётся одна активная заявка на роль.
2. Business Admin получает минимально необходимую карточку заявки.
3. Admin проверяет identity вне доверия к username/display name и принимает решение по точному sender ID.
4. Решение сохраняется атомарно и в audit.
5. После approval пользователь становится Creator; отдельный admin approval каждой Feature не требуется.

### 6.3. Проверка дублей

1. Для Creator и текущей версии Draft система использует Catalog для сужения продукта/области.
2. Выполняется bounded Jira search только в фиксированном проекте и типе задачи.
3. Creator получает ограниченный список кандидатов и объяснение сходства.
4. Если выбран существующий дубль, новый create не выполняется, а Draft закрывается как связанный с известной задачей.
5. Если Creator явно выбирает «не дубль», процесс продолжается.
6. Если кандидатов нет, проверка считается завершённой без дополнительного действия пользователя.

### 6.4. Автоматический create

Create выполняется детерминированным plugin-кодом, а не LLM, как только одновременно выполнены условия:

- sender identity присутствует и соответствует владельцу Draft;
- активна роль Creator;
- Draft не изменился после проверок;
- заполнены все обязательные Jira-поля;
- description содержательно заполнен;
- маршрут и значения Jira options допустимы;
- duplicate check актуален для текущей версии Draft;
- при наличии кандидатов Creator принял явное решение;
- отсутствует активная или завершённая posting operation для того же payload.

Preview и отдельная кнопка create отсутствуют.

### 6.5. После create

1. При подтверждённом ответе Jira сохраняются issue ID/key и ссылка.
2. Creator получает результат.
3. PO получает Telegram-уведомление по принятому маршруту.
4. Plugin не меняет статус, assignee или reporter и не выполняет transition.
5. Дальнейшая работа идёт по стандартному процессу Jira.

### 6.6. Неоднозначный timeout

Если POST мог дойти до Jira, но ответ не получен:

- операция переводится в `UNKNOWN`;
- Jira key не считается известным и не выдумывается;
- автоматический повторный POST запрещён;
- Draft и payload блокируются от повторной отправки;
- Technical Owner выполняет ручную reconciliation;
- только подтверждённая найденная задача может быть связана с операцией;
- дальнейшее действие без найденной задачи требует отдельного ручного решения, но не автоматического retry.

## 7. Объём MVP

### 7.1. Входит

- Telegram DM для текста и voice messages;
- транскрипция Whisper `medium`;
- structured Draft и уточняющий диалог;
- Guest/Creator/Admin RBAC;
- admin approval identity и роли;
- отдельный versioned Knowledge Catalog;
- bounded duplicate search в Jira с catalog narrowing;
- автоматический create FPF Feature для Creator;
- Telegram-уведомление Creator и PO;
- SQLite state, audit, retention, backup/restore;
- production deployment в отдельном Docker-контейнере;
- fail-closed обработка неопределённого результата.

### 7.2. Не входит

- preview Jira-задачи;
- кнопка «Создать в Jira» и confirmation token;
- отдельный admin approval каждой Feature;
- создание для Guest;
- изменение существующих Jira-задач;
- автоматические Jira transitions;
- назначение assignee/reporter;
- собственная ML-модель;
- Miro online sync;
- SSO;
- вложения и групповые чаты;
- произвольный JQL, URL или HTTP от пользователя/модели;
- custom Jira correlation field;
- автоматический retry POST после `UNKNOWN`;
- отдельный прикладной backend вне OpenClaw plugin.

## 8. Бизнес-обязательные данные Feature

Для create обязательны:

- project `FPF`, id `18100`;
- issue type `Feature`, id `11500`;
- `summary`;
- содержательный `description` по бизнес-шаблону;
- `Marketing Required` (`customfield_16203`);
- `Category` (`customfield_13200`);
- `Moscow` (`customfield_15204`);
- `Impacted Metrics` (`customfield_14902`).

Allowed options и техническая форма значений валидируются по Jira create metadata для Jira Server 11.3.8. Если обязательное значение неизвестно, система задаёт вопрос и не создаёт задачу.

`assignee` и `reporter` в payload не передаются; assignee остаётся `unassigned` согласно стандартному поведению Jira.

## 9. Показатели пилота

MVP должен позволять измерять без публикации содержимого идей:

- число начатых и готовых Draft;
- долю заявок на Creator и решения по ним;
- число successful/failed/unknown create;
- долю идей, остановленных как дубль;
- время от начала Draft до готовности и create;
- долю созданных Feature, где PO изменил продукт/маршрут, если такие данные доступны законным способом;
- latency LLM, Jira и transcription;
- rate-limit и security blocks.

Целевые бизнес-значения метрик должны быть согласованы после накопления baseline пилота.

## 10. Бизнес-риски и меры

| Риск | Мера MVP |
|---|---|
| Ошибочная identity | Только admin decision по host-derived sender ID |
| Создание дубля | Catalog narrowing, bounded Jira search и решение Creator |
| Раскрытие Jira Guest | Детали дублей только Creator |
| Выдуманные поля | Server-side whitelist и metadata/options validation |
| Двойной create | Атомарная operation claim; `UNKNOWN` блокирует повтор |
| Потеря ответа Jira | Fail closed и ручная reconciliation |
| Неверная маршрутизация | Versioned Catalog и допустимые Jira options |
| Утечка секретов | SecretRef/защищённое окружение, redaction, публичные документы без секретов |
| Нехватка ресурсов STT | Ресурсы под Whisper `medium` входят в предпосылки production |
| Устаревший OpenClaw | Контролируемое обновление отдельного контейнера до последнего стабильного релиза |

## 11. Бизнес-критерии приёмки

### BAC-01

Guest может подготовить Draft, но ни одним путём не создаёт Jira Feature и не видит детали дублей.

### BAC-02

Только решение Business Admin по trusted sender ID переводит Guest в Creator; решение аудируется.

### BAC-03

Creator не видит preview и не нажимает кнопку create: после готовности Draft и завершённого решения по дублям создаётся ровно одна Feature.

### BAC-04

Feature создаётся в production FPF как Feature, содержит все обязательные поля и содержательный description; assignee/reporter не передаются.

### BAC-05

При найденном дубле Creator видит кандидатов и принимает решение; Guest не получает их детали.

### BAC-06

После успешного create Creator и соответствующий PO получают Telegram-уведомление, а дальнейший workflow выполняется стандартными средствами Jira.

### BAC-07

При timeout с неизвестным результатом нет автоматического повторного POST; операция блокируется до ручной reconciliation.

### BAC-08

Voice message корректно транскрибируется Whisper `medium`, а пользователь может исправить текст до готовности Draft.

### BAC-09

MVP работает в отдельном production Docker-контейнере OpenClaw на зафиксированном последнем стабильном релизе.

### BAC-10

Knowledge Catalog имеет версию и контрольную сумму; способ его сбора и обновления оформлен отдельным согласованным решением до публикации production-каталога.
